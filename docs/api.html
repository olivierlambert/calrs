calrs v2 Documentation

REST API

calrs has a small JSON API under /api/v1 for integrations: list your event types, read their bookable times, read the bookings you host, and book, cancel or ask for a new time on a guest’s behalf. It runs inside calrs serve; there is nothing to install or enable.

The API is deliberately small. Everything it does, the dashboard or the booking page already does, through the same code: a booking made through the API is checked, stored, emailed, written to calendars and texted exactly like one made on the booking page.

OpenAPI document and interactive reference

  • /api/v1/openapi.json: the OpenAPI 3.1 description of the API, generated by calrs from its own handlers, so it always matches the version you run. Every operation, its parameters and request body, the answer of each status with the error codes it can carry, the headers, and the two security schemes with the scope each operation needs. Its servers entry and OAuth URLs are your base URL (CALRS_BASE_URL). It is public (it describes the API and holds no data): point a client generator or an API tool at it.
  • /api/docs: an interactive reference built from that document, for signed-in users (also linked from Profile & Settings → API tokens). It is Swagger UI, shipped inside the calrs binary: the page loads nothing from another site. To try a request, choose Authorize, paste a personal access token into personalAccessToken, then Try it out on an operation. The page never sends your session cookie (the API would ignore it anyway), and the token stays in the page’s memory until you leave it. The requests are real: POST /bookings books, and emails the guest. Authorize offers the personal token only: the page cannot complete the OAuth flow, so it hides the oauth2 scheme, which the JSON document still describes for applications.

Authentication

Every request carries a Bearer token:

Authorization: Bearer <token>

Cookies never authenticate the API, so a page you visit cannot use your signed-in session to call it (there is no CSRF to defend against). Requests from a browser page of another origin (an Origin header that is not the calrs origin) are refused, and the API sends no CORS headers.

There are two kinds of token.

Personal access tokens

For your own scripts. Create one at Profile & Settings → API tokens (/dashboard/settings/api-tokens): give it a name, choose its permissions and when it expires (7, 30, 90 or 365 days, or never). The token is shown once, when it is created; calrs stores only its SHA-256 hash. It looks like calrs_pat_ followed by 43 characters. The page lists your tokens (name, the first characters, permissions, creation, expiry, last use) with a Revoke button. A user holds at most 20.

By default only administrators can use the REST API, with a personal token or an OAuth application: both read guest names, addresses and notes, so letting every user pull them programmatically is the operator’s call. Admin panel → Sign-in and security → API tokens → Let all users use the REST API opens it to everyone. Turning it off again stops the personal tokens and the API grants of users who are not administrators at once (they work again if it is turned back on), and they cannot approve a new API application meanwhile (the consent answers access_denied); an administrator who is demoted loses the use of theirs the same way. MCP clients are not affected by the switch.

OAuth applications

For third-party applications acting for many users, calrs’s OAuth server (the one MCP clients use, see MCP integration) issues tokens for the API as a second resource:

  • resource: <base-url>/api/v1 (metadata at /.well-known/oauth-protected-resource/api/v1; the 401 challenge names it).
  • scopes: the four below. Omitting scope requests all four.

Registration, consent, PKCE, token lifetimes (one-hour access tokens, rotating refresh tokens, 30-day grants) and revocation work as described for MCP. A grant is bound to its resource: an MCP token does not open the API, an API token does not open /mcp, and the scopes of one resource cannot be requested for the other. When the API is closed to a user, the consent page says so and offers no Allow button. API grants appear under Profile & Settings → Connected apps with their permissions, and are revoked there.

The rules both follow

  • A token acts as its user, and the user is checked again on every request: a disabled account is refused at once.
  • Two-factor authentication: a token is worth what the session that made it was worth. When the admin requires MFA, a token created (or a grant approved) by a local account from a session that had not passed it stops working, as that session does.
  • Whatever signs a user out everywhere also deletes their tokens: suspending the account, calrs user set-password, calrs user reset-mfa, enrolling, disabling or regenerating two-factor authentication, linking to SSO. Re-enabling a suspended account brings no token back.
  • The admin panel’s per-user Revoke connected apps also deletes the user’s API tokens, and its count includes them.
  • An admin impersonating a user cannot create or revoke that user’s tokens.

Scopes

ScopeAllows
event-types:readGET /event-types, GET /event-types/{id}
slots:readGET /event-types/{id}/slots
bookings:readGET /bookings, GET /bookings/{id}
bookings:writePOST /bookings, POST /bookings/{id}/cancel, POST /bookings/{id}/request-reschedule

A missing scope answers 403 with insufficient_scope, and a WWW-Authenticate header naming the scope needed.

Who can see and do what

The API gives a user no more than the dashboard does, and an administrator no more than any other user: like MCP, there is no global admin bypass.

  • Event types you manage: the personal ones you own, and the team ones of teams you administer. Internal event types the booking directory offers you are listed too, read-only ("manageable": false): no slots, no bookings.
  • Slots and booking for a guest: event types you manage.
  • Bookings you host: the bookings of event types you own, the bookings a round-robin team assigned to you, collective bookings of your team (unless you are excluded from that event type), and bookings you claimed as a watcher. That is the rule of host notes, which these readers may see.
  • Cancel and request a reschedule: as on the dashboard, the owner of the event type. Another host gets 403 when the token can read bookings; a token with bookings:write alone gets the same 404 as for a booking that does not exist.

Anything else answers 404, whether it exists or not.

Never returned: credentials, the booking’s cancel, reschedule or approval tokens, other users’ data, and anything from your calendars beyond what the slot computation makes of it (no event titles, no calendar names).

Conventions

  • JSON only. Request bodies need Content-Type: application/json (415 otherwise) and are limited to 16 KiB, 1.5 MiB for POST /bookings, which can carry long answers (413). Unknown fields and unknown query parameters are refused (400).
  • Times are RFC 3339. calrs answers in UTC (2026-11-10T08:00:00Z).
  • Every answer carries Cache-Control: no-store.
  • Lists are paged with an opaque cursor: pass next_cursor back as cursor until it is null. A page can be short, even empty, and still have a next cursor (permission and time filters run after the page is read).
  • Errors always have this shape:
{"error": {"code": "slot_unavailable", "message": "This slot is no longer available."}}

code is stable; message is English text for people and may change.

Rate limits

  • 300 requests per minute per token (per OAuth grant, or per personal token).
  • On top of that, slot reads and every POST: 60 per 5 minutes per user, shared by all of the user’s tokens.
  • Bookings created through the API: 50 per user per 24 hours (429 daily_limit_reached; a place is taken before the booking is made, so concurrent requests cannot pass the cap, and given back when the booking is refused), each with at most 10 additional attendees whatever the event type allows on its booking page (422 too_many_attendees). Every booking emails the guest, the attendees and the hosts from the instance, so the API cannot be used to send mail without bound.

A request without a token gets 401 with WWW-Authenticate: Bearer resource_metadata="...", scope="..." and no error code (RFC 6750 section 3.1); an invalid or expired token adds error="invalid_token".

       "label": "I agree to the privacy policy", "help": null,
       "required": true, "options": [], "consent": true,
       "link_url": "https://example.com/privacy", "in_calendar": false}

}

scheduling_mode is round_robin or collective for a team event type. phone says whether a booking asks for the guest’s phone number (off, optional, required). The location’s value (a meeting link, an address) is not returned here. questions are the event type’s booking questions, in form order, with the key and option ids that POST /bookings takes in answers; null when you do not manage the event type (only a manager can book it).

GET /api/v1/event-types/{id}/slots

Query: from and to (dates, YYYY-MM-DD, inclusive, at most 31 days), timezone (IANA name, default the event type’s). The days are the guest’s days in that timezone.

The slots are computed by the booking page’s own engine, after the same on-demand calendar sync: weekly hours and date overrides, minimum notice, buffers, the booking horizon and bookable dates, frequency limits, time off, synced calendar events and bookings (pending requests that hold their slot included), shared resources, and for a team event type its members by scheduling mode (any member free for round robin, all for collective).

GET /api/v1/event-types/6c1e4f0a-.../slots?from=2026-11-10&to=2026-11-10&timezone=Europe/Paris

{
  "event_type_id": "6c1e4f0a-...",
  "timezone": "Europe/Paris",
  "from": "2026-11-10",
  "to": "2026-11-10",
  "slots": [
    {"start": "2026-11-10T08:00:00Z", "end": "2026-11-10T08:30:00Z",
     "date": "2026-11-10", "time": "09:00"}
  ]
}

date and time are the slot in the requested timezone; pass start back to book it. Like the booking page, the list leaves out wall times that do not name a single instant (the hour repeated when clocks go back), which the booking check would refuse.

GET /api/v1/bookings

Query: cursor, status (pending, confirmed, cancelled, declined), from and to (RFC 3339; bookings starting at or after from, before to). Ordered by start time, in UTC. Bookings made before calrs 1.20 store their time as a wall clock in the event type’s timezone; they are filtered exactly but sort among the others by that wall clock, so on an instance that has them the order near those rows can be off by the timezone’s offset.

{
  "bookings": [
    {
      "id": "1f6a...", "uid": "0b7d2e0e-...@calrs", "status": "confirmed",
      "start": "2026-11-10T08:00:00Z", "end": "2026-11-10T08:30:00Z",
      "created_at": "2026-11-07T09:12:44Z",
      "event_type": {"id": "6c1e4f0a-...", "slug": "intro", "title": "Intro call", "team_id": null},
      "guest": {"name": "Jeanne Martin", "email": "jeanne@example.com",
                "phone": null, "timezone": "Europe/Paris", "language": "fr",
                "notes": "About the renewal"},
      "answers": [{"key": "company", "label": "Company", "kind": "short_text",
                   "value": "Martin SARL", "option_ids": [], "consent": false,
                   "link_url": null, "answered_at": "2026-11-07T09:12:44Z",
                   "attested_by": null}],
      "attendees": ["paul@example.com"],
      "location": {"type": "link", "value": "https://meet.example.com/abc"},
      "host_notes": "Prefers mornings."
    }
  ],
  "next_cursor": null
}

uid is the iCalendar UID of the invitation (the one webhooks carry). guest.phone is null when the event type no longer asks for a phone number (its phone setting is off), even if the guest gave one before, as in emails, webhooks and calendar events. host_notes are the hosts’ own notes on the booking. answers are the guest’s answers to the event type’s booking questions, in the shape webhooks use; match choices on option_ids, value is for display.

GET /api/v1/bookings/{id}

{"booking": {...}}, the same object.

POST /api/v1/bookings

Books an event type you manage for a guest.

{
  "event_type_id": "6c1e4f0a-...",
  "start": "2026-11-10T08:00:00Z",
  "timezone": "Europe/Paris",
  "name": "Jeanne Martin",
  "email": "jeanne@example.com",
  "notes": "About the renewal",
  "phone": "+33 6 12 34 56 78",
  "attendees": ["paul@example.com"],
  "language": "fr",
  "answers": {
    "company": "Martin SARL",
    "topics": ["o1", "o2"],
    "privacy": true
  }
}
  • start must be one of the event type’s slots (as GET .../slots lists them); timezone is the guest’s (default the event type’s), stored with the booking and used in the guest’s emails.
  • notes, phone, attendees and language are optional. phone follows the event type’s phone setting (required, optional, or ignored) and is stored in E.164. attendees is limited by the event type’s additional guests setting. language is the language of the guest’s emails and SMS; by default the language you set in calrs, else English. When the instance addresses German speakers formally (Admin panel, German form of address), de becomes de-formal, as on the booking page.
  • No invite is needed for internal or private event types: you manage them. None is used up either.
  • answers carries the guest’s answers to the event type’s booking questions, keyed by question key: a string for short_text (at most 500 characters) and long_text (at most 5000), the option id for single_choice, an array of option ids for multiple_choice, true or false for checkbox. They are read by the booking page’s own rules and stored the same way, as the guest would have read the questions, so the hosts’ emails and calendar event (where the question allows it), the guest’s confirmation email and the webhooks show them as for a booking from the page. When answers is sent, every required question must be answered and a required checkbox (a consent) must be true. A question left out stores nothing, since the guest was never asked it (on the booking page an unticked box is stored as “no”). An unknown key, a key given twice, an option the question does not offer, an answer of the wrong type or over its length answers 400 invalid_request, naming the key.
  • A consent sent as true is your attestation, not the guest’s tick. The answer row, which is the consent record, stores who recorded it: your user id and name, and the credential (via api_token with the personal access token’s id, or oauth with the OAuth application’s client id). Reads and webhooks return it as attested_by ({"user_id", "name", "via", "credential_id"}, null on every answer the guest gave). Hosts see such a consent as “Agreed, recorded by” you on the bookings and notes pages and in their emails; the guest’s emails say it was recorded on their behalf by you, never “You agreed”. Only send true when the guest did agree, to you. The record stays with the booking for as long as its answers do, and is not affected by the 24-hour purge of the API’s own logs.
  • Without answers, no question is asked, even required ones: you are booking for the guest, as with calrs booking create, and the booking has no answers. This is how integrations written before answers keep working.
  • notes is stored as given either way, whatever the event type’s notes field setting.

The booking goes through the booking page’s own code: the same validation, a re-check of the time against the slot engine and of the shared resources under the booking lock, the same pending-or-confirmed decision (an event type that requires approval creates a pending request, and the host is asked to approve it), the same emails to the guest, the attendees and the hosts, the same calendar write-back, meeting link, watcher notifications, SMS and webhooks (booking.created or booking.requested). Cancel queues booking.cancelled (by the host) or booking.declined, as the dashboard does; a reschedule request queues nothing until the guest picks a new time.

201 Created. The answers of the three writes carry the whole booking only when the token also has bookings:read; a token with bookings:write alone gets {"booking": {"id", "status"}}.

{"booking": {"id": "1f6a...", "status": "confirmed", "...": "..."}}

The booking object is the one GET /bookings/{id} returns, without host_notes; keep its id to follow the booking. Reads follow the host rule: a team admin who books a round-robin event type assigned to another member, and is neither its owner nor that member, is not one of the booking’s hosts, so GET /bookings/{id} and the list answer 404 and leave it out for them afterwards (the webhooks of the event type still report it).

Idempotency-Key: send a key (1 to 255 visible ASCII characters) to make retries safe. The first answer with that key is kept 24 hours, per user, and replayed for a retry with the same body, answers included (with Idempotency-Replayed: true); the same key with another body answers 422 idempotency_key_reused, and a retry while the first request still runs 409 idempotency_in_progress. Server errors are not kept, so the request can be retried with the key. While the first request runs its key is leased and the lease renewed, so a slow booking is never run twice; a lease left two minutes without renewal (the server stopped) is released. A replay checks again that you may still book the event type (else 404) and is shaped by the token’s scopes like any answer. The kept answers contain the guest’s details; they are deleted after 24 hours, and with the user.

Refusals: 409 slot_unavailable (the time is not, or no longer, offered), 409 limit_reached (a booking frequency limit), 422 too_soon (inside the minimum notice), 422 outside_booking_window, 400 for invalid input.

POST /api/v1/bookings/{id}/cancel

Body (optional): {"reason": "Double booked"}.

What the dashboard’s cancel button does: a confirmed booking is cancelled, a pending request declined; the calendar copies and resource reservations are deleted, the guest, the attendees and the host are emailed (with the reason), the guest texted. Answers {"booking": {...}} with its new status. A booking already ended answers 409 booking_not_active.

POST /api/v1/bookings/{id}/request-reschedule

Body: none, or {}.

What the dashboard’s reschedule button does: the guest gets a new link and the “pick a new time” email, and the booking keeps its time until they choose one. 409 no_bookable_dates when the event type has no bookable day left. This is the only reschedule v1 offers, as on the dashboard: moving a booking to a time you choose is not in v1. While the guest has not answered an earlier request, another one is refused (409 reschedule_already_requested), so no second link is made. To remind the guest, send {"resend": true}: the same request is emailed again, with the same link, at most once an hour (409 resend_too_soon; 409 no_reschedule_pending when none is waiting). The dashboard has the same Resend request button.

Example

TOKEN=calrs_pat_...
BASE=https://cal.example.com/api/v1

curl -s -H "Authorization: Bearer $TOKEN" "$BASE/event-types"

curl -s -H "Authorization: Bearer $TOKEN" \
  "$BASE/event-types/$ET/slots?from=2026-11-10&to=2026-11-14&timezone=Europe/Paris"

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Idempotency-Key: crm-4711" \
  -d '{"event_type_id":"'$ET'","start":"2026-11-10T08:00:00Z","timezone":"Europe/Paris","name":"Jeanne Martin","email":"jeanne@example.com"}' \
  "$BASE/bookings"

Versioning

The version is in the path. Within v1, fields may be added to answers and new endpoints may appear; nothing is removed or changes meaning. A change that would break a client gets /api/v2.
