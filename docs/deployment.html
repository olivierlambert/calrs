calrs v2 Documentation

Deployment

This guide covers v2, currently a prerelease. Read Upgrading to v2 before using an existing data directory. The examples use next; choose an exact tag from Releases for a repeatable deployment.

Docker / Podman (recommended)

Pre-built images are available on GitHub Container Registry for amd64 and arm64:

docker run -d --name calrs \
  -p 127.0.0.1:3000:3000 \
  -v calrs-data:/var/lib/calrs \
  -e CALRS_BASE_URL=https://cal.example.com \
  ghcr.io/olivierlambert/calrs:next

Podman works as a drop-in replacement — just use podman instead of docker in all commands. The Containerfile (Dockerfile) is compatible with both runtimes.

latest follows stable releases; next follows prereleases. An exact prerelease tag looks like ghcr.io/olivierlambert/calrs:2.0.0-beta.4. The loopback port binding above assumes a reverse proxy on the host; adapt it if your proxy runs in a separate container.

The image uses a multi-stage build:

  • Builder: rust:slim-trixie — compiles the release binary
  • Runtime: debian:trixie-slim — minimal image with only ca-certificates
  • Runs as unprivileged calrs user
  • Data stored in /var/lib/calrs
  • Templates bundled at /opt/calrs/templates/

To build from source instead: docker build -t calrs .

Docker Compose / Podman Compose

services:
  calrs:
    image: ghcr.io/olivierlambert/calrs:next
    ports:
      - "127.0.0.1:3000:3000"
    volumes:
      - calrs-data:/var/lib/calrs
    environment:
      - CALRS_BASE_URL=https://cal.example.com
    restart: unless-stopped

volumes:
  calrs-data:

Works with both docker compose and podman-compose.

RPM (RHEL / Fedora)

Community-maintained RPM packages are published on Copr by @wallon-ines for Enterprise Linux 9 and 10:

# Enable the repo (RHEL 9/10, Rocky, AlmaLinux, ...)
sudo dnf copr enable missd/calrs
sudo dnf install calrs

# Start the service
sudo systemctl enable --now calrs
  • Copr repository: https://copr.fedorainfracloud.org/coprs/missd/calrs/
  • RPM spec source: https://gitlab.famillewallon.com/rpm-packages/calrs

These packages are not maintained by the calrs project itself; for issues with the package (versioning, dependencies, systemd unit), reach out via the Copr/GitLab links above.

Binary + systemd

# Build from source
cargo build --release

# Create the service account and data directory first (new installation)
sudo useradd -r -s /bin/false -m -d /var/lib/calrs calrs
sudo install -d -o calrs -g calrs -m 750 /var/lib/calrs

# Install the binary and matching templates (replace the whole tree:
# copying into an existing templates/ would nest the new one inside it)
sudo install -m 755 target/release/calrs /usr/local/bin/calrs
sudo rm -rf /var/lib/calrs/templates
sudo cp -r templates /var/lib/calrs/templates

# Install the service
sudo cp calrs.service /etc/systemd/system/
sudo systemctl daemon-reload
# Set the public URL before starting (see below)
sudo systemctl edit calrs
sudo systemctl enable --now calrs

In the service override opened by systemctl edit, set:

[Service]
Environment=CALRS_BASE_URL=https://cal.example.com
Environment=CALRS_TRUSTED_PROXIES=127.0.0.1,::1

The included unit runs from /var/lib/calrs, where it finds templates/, and listens on 127.0.0.1:3000. Put your TLS reverse proxy on that host, or deliberately change the bind address and proxy trust for a different topology. Install matching templates whenever you replace the binary: stop the service, replace the binary, remove /var/lib/calrs/templates and copy the new templates/ in its place, then start the service.

systemd service

The included calrs.service has security hardening:

  • NoNewPrivileges=true
  • ProtectSystem=strict
  • ProtectHome=true
  • ReadWritePaths=/var/lib/calrs
  • PrivateTmp=true
  • ProtectKernelTunables=true
  • ProtectControlGroups=true
  • Restart=on-failure with 5-second delay

From source (development)

cargo build --release --locked
./target/release/calrs serve --port 3000

Then register at http://localhost:3000 — the first user becomes admin.

Reverse proxy

calrs listens on port 3000 by default. Put nginx or caddy in front for TLS.

nginx example

server {
    listen 443 ssl http2;
    server_name cal.example.com;

    ssl_certificate /etc/letsencrypt/live/cal.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/cal.example.com/privkey.pem;

    # Room for the 2 MB logo and avatar uploads (nginx's default is 1 MB).
    client_max_body_size 3m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Caddy example

cal.example.com {
    reverse_proxy localhost:3000
}

Which paths to expose

Exposing every path, as the examples above do, is the default and is safe once the instance is set up: everything beyond the guest pages asks for a session, a token or an OAuth grant. Two things come first. The first account registered becomes the admin, so register it before the instance is reachable from the internet. And anyone may create an account at /auth/register while registration is open, so turn it off in the admin panel, or limit it to your email domains, if strangers should not sign up. Some operators still prefer a public site that serves guest pages only, and keep the rest on an office network or a VPN. These are the groups of paths calrs serves:

PathsWhat they serveWho needs them
/u/, /team/, /t/, /g/Booking pages, invite links, old team links (redirects)Guests
/booking/Cancel, reschedule and calendar file links in guest emails; approve, decline and claim links in host and watcher emailsGuests and hosts, from their mailbox
/avatar/, /team-avatar/, /fonts/, /static/intl-tel-input/, /logo, /logo/dark, /brand-logo, /favicon, /favicon.ico, /accent.css, /embed.jsFiles the booking pages and embeds loadGuests
/, /auth/, /dashboard/Sign-in (/ redirects there) and the dashboard. With SSO, /auth/oidc/callback must be reachable from the users’ browsersHosts and admins
/api/v1/, /api/docs, /static/swagger-ui/REST API, its OpenAPI document and its referenceAPI clients, signed-in users
/mcp, /oauth/, /.well-known/oauth-authorization-server, /.well-known/oauth-protected-resource/MCP server and the OAuth endpoints MCP and API clients sign in throughAI assistants, OAuth API clients
/{slug}, /{slug}/bookSingle-user links from before /u/Only if such links are still shared

Keep /booking/ public even when hosts work from the office: the approve and decline buttons in their emails point there. An MCP or API client needs its paths reachable from wherever it runs.

A restriction in the proxy only holds if calrs cannot be reached around it. Publish its port on the loopback address only (-p 127.0.0.1:3000:3000 with Docker, 127.0.0.1:3000:3000 under ports: in Compose), or keep it off the published ports and reach it over the proxy’s own network. With Docker Engine older than 28.0.0, a port published on 127.0.0.1 can still be reached by hosts on the same local network segment, so upgrade Docker, or filter that port in the host’s firewall, or use the proxy’s network instead.

An nginx version that serves guest pages to everyone and the rest to one network only:

server {
    listen 443 ssl http2;
    server_name cal.example.com;
    # ssl_certificate lines as above
    client_max_body_size 3m;

    # Set here, inherited by every location below.
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Guest pages, email links and the files they load: public.
    # Old single-user links (/{slug}, /{slug}/book) are not listed, so guests
    # outside the network get 403 for them: add a location if you still
    # share such links.
    location ~ ^/(u|team|t|g|booking|avatar|team-avatar|fonts|static/intl-tel-input)/ {
        proxy_pass http://127.0.0.1:3000;
    }
    location ~ ^/(logo|logo/dark|brand-logo|favicon|favicon\.ico|accent\.css|embed\.js)$ {
        proxy_pass http://127.0.0.1:3000;
    }

    # Sign-in, dashboard, API, MCP, OAuth: office network only.
    location / {
        allow 192.0.2.0/24;
        deny all;
        proxy_pass http://127.0.0.1:3000;
    }
}

CALRS_BASE_URLPublic URL (required for OIDC callbacks and email action links)http://localhost:3000
CALRS_ALLOW_PRIVATE_HOSTSComma-separated hostnames or IP addresses allowed to resolve to private IPs for CalDAV/EWS (SSRF opt-out)(none)
CALRS_TRUSTED_PROXIESComma or space separated addresses and CIDR ranges of the reverse proxies whose X-Forwarded-For calrs believes for its rate limits, or none to trust no peer. A /0 range is refused. See Trusted proxiesloopback, private, unique local and link-local ranges

A failing source is retried at this interval too, so longer intervals can delay the email warning its owner (sent after at least three failures spanning more than an hour)0 (no minimum: each source about once an hour, see below)
CALRS_SYNC_CONCURRENCYHow many calendar sources the background sync may sync at once, never more than one per server. Capped at 8: syncs share the database’s five connections with web requests4
CALRS_SECRET_KEYOptional external credential-encryption key: a base64-encoded 32-byte key. Preserve the same key across restarts and restoresGenerated secret.key in the data directory

CALRS_BASE_URL, CALRS_ALLOW_PRIVATE_HOSTS and CALRS_TRUSTED_PROXIES can also be set without environment variables, from the admin panel (System settings: base URL, private hosts, Trusted proxies); the first two also from the CLI (calrs config general). The stored value is persisted in the database; when the matching environment variable is set it takes precedence at runtime and the field is read-only. System settings check every field before saving any, so a refused value saves nothing from the form. The other variables (CALRS_DATA_DIR, RUST_LOG, and CALRS_SECRET_KEY) are bootstrap settings and remain environment-only.

Background calendar sync

Besides the on-demand refresh of booking pages, calrs serve syncs calendar sources in the background. Once a minute it syncs enough sources for every one to come round about once an hour: one per minute up to 60 sources (as in earlier versions), then the number of sources divided by 60 (24 per minute for 1,440 sources). Sources due their daily full resync go first; then the ones synced longest ago. Up to CALRS_SYNC_CONCURRENCY syncs run at once, but never two against the same server (scheme, host and port), so one CalDAV or Exchange server sees one background sync at a time; managed Exchange sources count against the server of the global Exchange endpoint. Microsoft 365 and Google calendars, which throttle each user separately, count each source on its own. A slow server holds one slot only: the other slots carry on with sources on other servers, and the next minute starts on time. A sync still running after 10 minutes is stopped and counts as a failure of its source. Reminders, request expiry and write-back retries run in a task of their own and never wait for any of this. A source being synced already is not synced twice: a booking page that finds its host’s source being synced shows the cached times without waiting, and the Sync button waits up to 20 seconds for it, and an approval up to 10 seconds, so that it checks the calendar that sync fetched. The calrs sync CLI is a separate process and is not coordinated with a running server.

Observability

calrs uses structured logging via the tracing crate. All log output goes to stderr, captured by systemd journal or Docker logs.

Log levels

# Default (recommended)
RUST_LOG=calrs=info,tower_http=info

# Verbose (includes per-request details)
RUST_LOG=calrs=debug,tower_http=debug

# Errors only
RUST_LOG=calrs=error

What’s logged

Viewing logs

# systemd
journalctl -u calrs -f

# Docker
docker logs -f calrs

Backup

A complete backup includes calrs.db, the credential key and uploaded files. The key is normally $CALRS_DATA_DIR/secret.key; if CALRS_SECRET_KEY supplies it, preserve that external secret instead. Without the key, stored calendar passwords, OAuth credentials and MFA secrets cannot be decrypted.

To make a consistent database snapshot while the server runs:

sqlite3 /var/lib/calrs/calrs.db ".backup /path/to/backup.db"

Also copy the key and uploaded assets, and retain service/environment configuration and the deployed version. For a filesystem backup of the whole data directory, stop calrs first and copy the directory, preserving ownership and any WAL files. Do not copy only a live SQLite main file while writes continue. Restore into a stopped instance with the matching key, then check access and calendar sync. See Upgrading to v2 for rollback.
